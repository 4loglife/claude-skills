# 단계별 체크리스트

각 항목 뒤 괄호는 출처 강의. "확인" 줄은 증거를 어디서 찾을지에 대한 힌트다.

---

## A. 콜드 스타트 — 저장소가 에이전트에게 준비됐나

**콜드 스타트 테스트(3강):** 대화 기록 없이 저장소만 읽은 새 에이전트가 답할 수 있어야 한다.

| # | 항목 | 확인 |
|---|---|---|
| A1 | 어떤 제품을 만드는지 알 수 있다 (3) | README, AGENTS.md 첫 부분 |
| A2 | 앱이 사용자를 위해 무엇을 해야 하는지 알 수 있다 (3) | 제품 문서, docs/PRODUCT* |
| A3 | 코드베이스 구성을 알 수 있다 (3) | ARCHITECTURE.md, 디렉터리 설명 |
| A4 | 표준 **시작** 명령이 하나로 정해져 있다 (3·6) | `npm run dev`, `make run`, init.sh |
| A5 | 표준 **검증** 명령이 하나로 정해져 있다 — 테스트·타입·린트를 한 번에 (2·6) | `make check`, `npm run check` |
| A6 | 지금 진행 중인 작업을 알 수 있다 (3) | PROGRESS.md, feature_list |
| A7 | 중요한 품질 기준이 적혀 있다 (3) | AGENTS.md 하드 제약, 품질 문서 |
| A8 | 진입 파일이 짧은 라우터다: 개요 + 빠른 시작 + 하드 제약 + 주제 문서 링크, 대략 50~200줄 (4) | `wc -l AGENTS.md CLAUDE.md` |
| A9 | 진입 파일 안티패턴이 없다: 모든 지식을 한 파일에, 같은 규칙 반복, 아무도 안 보는 낡은 규칙, 거의 안 쓰이는 세세한 조건부 규칙, 긴 도구 설명서 (4) | 중복·길이·날짜 |
| A10 | 중요한 정보가 진입 파일 맨 위나 맨 아래에 있다 ("중간 손실") (4) | |
| A11 | 런타임과 의존성이 고정돼 있다: lock 파일, `.nvmrc`/`.python-version`, 필요하면 Docker·devcontainer (2) | |
| A12 | 도구 권한이 적절하다: 셸·테스트를 돌릴 수 있되 최소 권한 (2) | `.claude/settings*.json` |
| A13 | 문서가 코드와 맞는다 — 문서에 적힌 명령·경로가 실제로 존재한다 (3: 낡은 문서는 없는 것보다 위험) | 문서 속 명령/경로 대조 |
| A14 | 초기화 산출물이 있다: 첫 진행 기록, 안정적인 첫 커밋, 다음 실행이 볼 기능 목록 (6) | git log, feature_list |

**실패 신호(1강) — 과거 실행을 돌아볼 때 덧붙여 확인:**
에이전트가 시작 방법을 잘못 추론했나 / 제품과 안 맞는 디렉터리·추상화를 만들었나 / UI 껍데기만 만들고 멈췄나 / 다음 실행용 메모를 남겼나 / 새 세션이 5분 안에 상황을 파악할 수 있나.

## B. 세션 시작 — 이전 작업을 이어받을 수 있나

| # | 항목 | 확인 |
|---|---|---|
| B1 | 5분 안에 최근 작업을 파악할 수 있다 (5) | PROGRESS.md, 최근 커밋 메시지 |
| B2 | 현재 안정적인 시작 경로가 문서화돼 있고 **실제로 된다** (5·6) | 시작 명령 실행 |
| B3 | 미완료·깨진 항목이 명확히 적혀 있다 (5) | 핸드오프의 "깨지거나 미검증" |
| B4 | 이전 채팅을 안 읽어도 다음으로 할 가장 좋은 작업이 보인다 (5) | 핸드오프의 "다음 단계" |
| B5 | 설계 결정 기록이 있다 — 무엇을, 왜 (5) | decisions 로그, ADR |
| B6 | 시작 시점 검증이 초록이다 — 남의 실패를 내 작업으로 착각하지 않게 (12) | 검증 명령 실행 |

부트스트랩 계약 4조건(6강)으로 요약: 시작할 수 있다 · 테스트할 수 있다 · 진행 상황이 보인다 · 다음 단계를 안다.

## C. 작업 시작 — 범위와 완료 조건이 정해졌나

| # | 항목 | 확인 |
|---|---|---|
| C1 | WIP=1: 지금 active인 작업이 하나뿐이다 (7) | feature_list 상태 |
| C2 | 다음 작업 템플릿이 채워져 있다: 최우선 기능 / 왜 지금 / 통과 조건 / 이번에 건드리면 안 되는 것 (7) | |
| C3 | 범위가 "인덱싱 구현" 같은 한 줄이 아니라 확인 가능한 하위 단계로 쪼개져 있다 (7) | |
| C4 | 범위 표면이 대화가 아니라 **파일**에 기록돼 있다 (7) | |
| C5 | 완료 증거가 실행 가능하다 — "코드가 괜찮아 보임" ✗, "curl이 201 반환" ✓ (7) | |
| C6 | 기능 항목이 삼중 구조다: 동작 설명 + 검증 명령 + 현재 상태 (8) | feature_list 형식 |
| C7 | 크기가 "한 세션 안에 끝낼 수 있음" 수준이다 (8) | |
| C8 | 큰 작업이면 스프린트 계약이 있다: 목표 + 사용자 관점 완료 기준 (11) | |
| C9 | 평가 기준이 필요한 작업이면 루브릭(차원별 1~5점)이 있다 (11) | |
| C10 | VCR(검증된 작업 ÷ 활성 작업) = 1.0 이다 — 1.0 미만이면 새 작업 시작 금지 (7) | |

## D. 완료 판정 — 정말 끝났나

**3단계 종료 검사(9강): 앞 단계가 실패하면 다음 단계로 가지 않는다. 셋 다 통과해야 완료.**

| # | 항목 | 확인 |
|---|---|---|
| D1 | 1단계: lint·타입 검사 통과 (9) | 실행 결과 |
| D2 | 2단계: 테스트 통과 + 앱이 실제로 시작됨 (9) | 실행 결과 |
| D3 | 3단계: 완전한 사용자 흐름(엔드투엔드)이 실행됨 (9·10) | E2E 테스트 또는 직접 실행 기록 |
| D4 | 패스 게이트: 예상 워크플로가 실행됐다 / 성공 증거가 기록됐다 / 테스트 경로에 막는 오류가 없다 / 앱이 깨지거나 애매한 상태가 아니다 (8) | |
| D5 | 상태 전환(`passes: false → true`)을 에이전트가 손으로 바꾸지 않았다 — 검증이 통과해서 바뀌었다 (8) | feature_list diff |
| D6 | 핵심 기능 검증 전에 "그 김에 리팩터링"을 하지 않았다 (9) | diff 범위 |
| D7 | C2에서 정한 "건드리면 안 되는 것"을 건드리지 않았다 (7) | `git diff --stat` |
| D8 | 아키텍처 경계 규칙을 어기지 않았다 — 가능하면 린트·임포트 규칙으로 자동 검사 (10) | |
| D9 | 실패 메시지가 에이전트가 스스로 고칠 수 있게 구체적이다 ("빨간 펜") (9·10) | 검사 스크립트 출력 |
| D10 | 런타임 신호(로그·에러)를 확인했다 — 무엇이 일어났는지 (11) | |

D1~D3 중 하나라도 ❌ → **"완료 아님"**.

## E. 세션 종료 — 클린 상태로 끝나나

**클린 상태 5차원(12강): 빌드 · 테스트 · 진행 상황 · 산출물 · 시작.**

| # | 항목 | 확인 |
|---|---|---|
| E1 | 빌드 통과 (12) | 빌드 명령 |
| E2 | 모든 테스트 통과 (12) | 검증 명령 |
| E3 | 기능 목록과 진행 기록이 업데이트됐다 (9·12) | PROGRESS.md, feature_list diff |
| E4 | 디버그 흔적이 없다: `console.log`, `debugger`, 임시 `print`, 새로 생긴 TODO/FIXME, 임시 파일 (12) | grep, `git status` |
| E5 | 문서화되지 않은 반쯤 끝난 단계가 남아 있지 않다 (9) | |
| E6 | 수동 수리 없이 표준 시작 경로가 된다 (9·12) | 시작 명령 실행 |
| E7 | 다음 에이전트가 시작·검증 경로를 바로 실행할 수 있다 (9) | |
| E8 | 세션 핸드오프가 작성됐다: 완료 / 깨지거나 미검증 / 다음으로 가장 좋은 단계 (5) | |
| E9 | 작업이 원자적 커밋으로 저장됐다 (3: ACID) | `git log`, `git status` |

"나중에 정리"는 절대 정리하지 않는다는 뜻이다(12). ❌가 남으면 고치고 끝내거나, 최소한 핸드오프 E8의 "깨지거나 미검증"에 정확히 적는다.

## F. 루프·그래프 설계 전

### 루프 (13강)

| # | 항목 | 확인 |
|---|---|---|
| F1 | 목표가 한 문장이다 | goal 문서 |
| F2 | 완료 조건이 **기계로 확인 가능**하다 — 각 조건마다 명령이 있다 | |
| F3 | 범위가 "건드려도 됨 / 손대지 말 것"으로 나뉘어 있다 | |
| F4 | 매 단계 검증 방법(명령 순서)이 정해져 있다 | |
| F5 | 중단 조건이 있다: 성공 / 최대 턴 / N회 연속 진전 없음 / 혼자 못 푸는 차단 요인 | |
| F6 | 외부 상태 파일이 있다 — 라운드마다 갱신, 다음 라운드 시작 때 읽음 | loop state 파일 |
| F7 | 메이커와 체커가 분리돼 있다(서브 에이전트) — 체커는 문제를 찾는 게 일 | |
| F8 | 여러 루프를 병렬로 돌리면 워크트리로 격리한다 | |
| F9 | 프로젝트 설명을 반복하지 않게 스킬·진입 파일로 넘긴다 | |
| F10 | 위험 4가지를 의식했다: 검증 부채 · 이해 부패 · 인지 항복 · 토큰 폭발 | |
| F11 | `/goal`(목표 달성까지 반복)과 `/loop`(일정 간격 반복)를 혼동하지 않았다 | |

### 그래프 (14강)

먼저 **그릴 가치가 있는지** 5가지 기준: 독립적으로 쪼갤 수 있다 · 분기나 롤백이 있다 · 중간 상태를 저장할 가치가 있다 · 결과를 검수할 수 있다 · 협력 이득 > 조정 비용. 하나라도 아니면 단일 루프로 충분할 수 있다.

| # | 항목 |
|---|---|
| F12 | 어떤 루프가 어떤 루프에 결과를 넘기는지 답할 수 있다 |
| F13 | 누가 목표를 소유하는지 정했다 |
| F14 | 누가 거부·롤백할 수 있는지 정했다 |
| F15 | 어떤 지표는 움직이고 어떤 지표는 고정해야 하는지 정했다 (Goodhart 방지 앵커) |
| F16 | 루프들이 서로를 깎아먹는 충돌이 없는지 봤다 |
| F17 | 내 검토 대역폭이 노드 수를 감당할 수 있다 — 판단은 직렬 자원이다 |

F12~F15에 답하지 못하면 그래프를 그리지 않는다(14).

## G. 정기 감사 — 하네스가 부패하지 않았나

| # | 항목 | 확인 |
|---|---|---|
| G1 | 5개 하위 시스템이 모두 있다: 지시 · 도구 · 환경 · 상태 · 피드백 (2) | |
| G2 | 진입 파일 규칙마다 출처·적용 조건·만료 조건을 알 수 있다 (4) | |
| G3 | 더는 필요 없는 제약을 지웠다 — 모델이 좋아지면 하네스를 단순화 (12) | |
| G4 | 반복되는 리뷰 지적이 린트·검사 규칙으로 승격됐다 (10) | |
| G5 | 아키텍처 규칙이 문서가 아니라 커밋마다 도는 검사다 (10) | CI, pre-commit |
| G6 | 정리 루프가 있다: 낡은 문서 스캔 → 구조 위반 스캔 → 품질 등급 갱신 → 정리 PR → 벤치마크 재실행 (12) | |
| G7 | 정리 작업이 멱등적이다 — 두 번 돌려도 안전 (12) | |
| G8 | 품질 문서로 코드베이스 건강을 추적한다 (12) | |
| G9 | 하네스 변경 효과를 측정한다: 완료율 · 평균 재시도 · 사람 리뷰 전에 잡힌 버그 (12) | |
| G10 | 실패를 기록하고 원인을 분류한다: 작업 의도 / 컨텍스트 / 환경 / 검증 피드백 / 상태 관리 (1·2) | |
| G11 | 관측 가능성 두 층이 있다: 런타임 신호(무슨 일이) + 프로세스 산출물(왜) (11) | |
